## 一、第一步：随机状态管理核查（代码层面）

| 项 | 现状 | 判定 |
|---|---|---|
| Python / NumPy seed | `random.seed(seed)`、`np.random.seed(seed)` — `train_one` 开头 | ✅ |
| PyTorch CPU / CUDA seed | `torch.manual_seed(seed)`（该调用同时设置所有 CUDA 设备） | ✅ |
| 模型初始化前的随机状态 | 三个 seed 设置后才 `build_model()`；两次运行**初始化参数哈希完全相同** | ✅ 实测一致 |
| DataLoader generator | 未显式传 `generator`；`num_workers=0`（运行脚本与冒烟均为 0）→ 无 worker 种子问题 | ✅ |
| `worker_init_fn` | 未使用（因为不用多进程） | 不适用 |
| `SubsetRandomSampler` 的 batch 顺序 | 它会在选中的 552 个索引内**再随机排列**；本轮直接记录了 758 次 `__getitem__` 的实际调用顺序 | ✅ 两次运行顺序哈希相同 |
| 验证/测试 DataLoader | `shuffle=False` | 不引入随机 |

**结论：随机状态管理没有发现问题；抽样集合与 batch 顺序都可复现。**

## 二、第二步：短程复现测试（同代码、同 seed、同配置）

诊断脚本：`classify_project/scripts/diagnose_determinism.py`（只读诊断，不改训练流程）。
配置 = A1（552 真实 + 32 合成、`fixed-draws 552`、冻结权重），seed 42。

| 模式 | epoch | 初始化哈希 | batch 顺序哈希 | 前向最大差 | 梯度最大差 | 测试 QWK 差 | val QWK 差 |
|---|---:|---|---|---:|---:|---:|---:|
| 默认（非确定性） | 1 | 相同 | 相同 | **0.0** | **1.49e-08** | **0.0694** | 0.0312 |
| 默认（非确定性） | 5 | 相同 | 相同 | 0.0 | 1.49e-08 | **0.0245** | 0.0128 |
| 确定性模式 | 1 | 相同 | 相同 | 0.0 | **0.0** | **0.0** | 0.0 |
| 确定性模式 | 5 | 相同 | 相同 | 0.0 | **0.0** | **0.0** | 0.0 |

**关键读数**
1. 初始化和 batch 顺序**两次完全一致**——所以波动不是来自数据或种子管理；
2. 前向输出**逐位相同**（差 0.0），反向梯度差 **1.49e-08**（float32 量级）；
3. 这 1e-8 的梯度差在 35 步内被放大成 QWK 0.069；5 epoch（175 步）为 0.0245；
4. 1 epoch 的波动明显大于 5 epoch，因为此时 logits 接近均匀，微小扰动就能翻转 argmax。

**因此：波动来源已定位为 GPU 反向计算的非确定性**，而不是抽样、初始化或 DataLoader 顺序。
（上一版报告把这一步跳过了，结论下得太早。）

## 三、第三步：确定性模式可行性

设置：`torch.use_deterministic_algorithms(True, warn_only=True)`、
`cudnn.deterministic=True`、`cudnn.benchmark=False`、`CUBLAS_WORKSPACE_CONFIG=:4096:8`（CUDA 初始化前设置）。

> **按导师 2026-11-17 意见修订**：`warn_only=True` 只是可行性探路，**不是**严格确定性保证。
> 正式训练改用 `warn_only=False`（不支持确定性实现的算子直接报错），复检结果见
> `T3_确定性模式预检_20261117.md`。

| 项 | 结果 |
|---|---|
| 是否报"不支持确定性算子" | **未出现**（无 warning / 无 error） |
| 两次 5-epoch 的指标 | **完全相同**（QWK 差 0.0） |
| 梯度复现 | **完全相同**（差 0.0） |
| 5 epoch 耗时 | 12.3 s → **20.8 / 25.3 s**（约 1.7–2.1 倍） |
| 扣除固定开销后的每 epoch 增量 | 约 **+1.7 ~ 2.6 s/epoch** |

按 30 epoch 推算，每个 run 增加约 **50–80 秒**；9 次总计增加 **10 分钟量级**（非数小时）。

**限定（与导师一致）**：确定性模式保证的是**同硬件、同软件版本、同环境下**逐位可复现，
不保证跨 GPU / 跨版本的逐位一致。

## 四、结论与建议

1. **计数器修改保留**（已验证只增加记录）。
2. **随机性来源已查清**：不是抽样、不是初始化、不是 batch 顺序，而是 GPU 反向传播的非确定性。
3. **建议采用确定性模式（方案 B）跑 9 次**：
   - 代价约 1.7–2.1 倍耗时，绝对增量每 run 50–80 秒；
   - 收益（**按导师定稿表述**）：

     > 确定性模式减少了同一训练配置、同一随机种子及相同运行环境下由非确定性计算引入的
     > 重复运行差异，使同 seed 结果具有更好的计算可复现性。但 A0、A1、A2 的数据池与抽样
     > 机制并不相同，因此三组之间仍然存在训练数据组成、样本曝光及优化轨迹差异。确定性
     > 设置不能消除这些实验变异，也不能消除不同训练 seed 之间的差异。

     补充：A0 每轮遍历完整真实训练集（552 张），A1/A2 每轮从 584 张训练池抽 552 张，
     所以三组同 seed 是**种子层面的配对设计**，不是逐 batch 可一一配对的严格控制实验。
   - 需要一个小改动：在 `train_classifier.py` 加 `--deterministic` 开关，三组统一传入
     （已实现，见 `T3_确定性模式预检_20261117.md`）。
4. **必须披露**：DL-EX-027 的历史结果来自**未开确定性模式**的运行，
   T3 的 A0 不能与 DL-EX-027 的 A0 当作同协议数字直接比较，只能作历史参照。
5. **0.02 继续作为"实际意义参考幅度"，不是显著性线**；T3 的判定仍结合 3 个 seed 的配对差、
   方向一致性与离散程度。确定性模式只消除"同 seed 不可复现"这一类噪声，不消除数据本身的方差。
   **不得**把"超过 0.02 且三个 seed 同向"解释成统计显著或已排除所有噪声。
6. **诊断中的 test QWK 不再用于后续决策**（导师 2026-11-17）：不据这些短程 test 数字调配置、
   不据此判断 A0/A1/A2 优劣；正式训练只按验证集 QWK 选 checkpoint，模型冻结后 test 只评一次。
   本报告与预检中的 test QWK 仅留作内部诊断记录，不纳入 T3 正式结果表。
